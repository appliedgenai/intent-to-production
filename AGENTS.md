# Instructions for Intent to Production

Read PROJECT-GOALS.md, README.md, PAPER.md, WORKED-EXAMPLE.md and SOURCES.md before editing. Inspect rendered diagrams, not only captions. User instructions take precedence. Preserve the separate runtime-authority paper unless the user expands scope.

## Intended result

A senior platform leader should understand the investment decision in a six-minute visual brief. Practitioners should find layer responsibilities, concrete tool options, build/buy triggers, interface contracts, failures, ownership, patterns and meaningful metrics in the companion material. Keep the six-layer architecture central; use one short connected example to demonstrate it.

The thesis is to adopt broad coding capabilities while owning enterprise context, domain decisions, integration contracts and applicable release evidence. Explain how another team reuses these interfaces with its own domain evidence. A faster generator alone is not a business result.

## Boundaries to preserve

- Six layers are logical responsibilities, not six lifecycle phases, six mandatory products or six microservices. Control and evidence apply throughout.
- Separate tracker commitment, intended behavior in maintained specifications, transient run state, actual implementation and verified deployment. Define authority and conflict resolution; do not present the proposed split as a product limitation.
- Durable knowledge differs from task context. Graph traversal supplies known paths, not proof of complete impact coverage. Use search/catalog links first when sufficient; justify a graph with recurring useful queries and stewardship capacity.
- Preserve source permissions, provenance, effective dates and known gaps. An outage is not an authoritative empty result. A cached context manifest cannot grant continuing access after revocation.
- A purchased agent contains a built-in harness. Enterprise guidance, domain examples, feedback checks and release integration still need owners. Prompts and skills do not enforce permissions.
- Old evidence remains historical evidence. Review its applicability when a material input changes; hold unsupported claims, requalify affected behavior and justify retained results. Do not invalidate everything merely because a newer document or coding model exists.
- Distinguish the development agent from AI shipped in a product. Generator upgrades and runtime model/prompt changes have different implications. The onboarding feature in this example need not use an LLM at runtime.
- Bind the release to immutable artifacts, relevant configuration, applicable rules/cohort/effective time, required evidence and authorization. A branch name, checked task box or green dashboard is insufficient.
- Tracker synchronization and dashboard repair must not repeat a deployment. Define retry, duplicate/stale-event behavior and recovery owners.
- Preserve user authorization to publish. Do not invent additional confirmation requirements.

## Integrity and sources

Use current primary sources for changing product and standards claims. Attribute Birgitta Böckeler's articles on Martin Fowler's site to her. Keep historical product observations distinct from current documentation and date availability announcements. The six-layer stack is the author's synthesis, not an AWS/Kiro/Fowler standard.

Do not invent deployments, savings, incidents, benchmarks or personal experience. ONB-017 and all identifiers/results are synthetic. Specifications and scenario files are not executed tests. Product placements are candidate capabilities, not a tested procurement bundle. Own/build terminology must allow buying an implementation of an enterprise-owned contract.
